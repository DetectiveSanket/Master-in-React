    To clear up the confusion between "Context API" and useContext, 
    we first need to realize they aren't two different things competing 
    with each other.
    
    ⭐ They are TWO PARTS of the SAME TEAM! ⭐



┌──────────────────────────────────────────────────────────────────────────────┐
│  1️⃣   CONTEXT API vs useContext: What's the Difference?                     │
└──────────────────────────────────────────────────────────────────────────────┘

    🏠 THE PLUMBING ANALOGY:
    ────────────────────────
    
    - Think of the Context API as the entire plumbing system of a house.
      It's the pipes, the water tank, and the plan for how water gets to every room.
    
    - useContext is simply the faucet (the tap) you install in a specific 
      room to get the water out.


    ┌─────────────────────────────────────────────────────────────────────┐
    │                                                                     │
    │   📦 Context API                                                    │
    │   ─────────────                                                     │
    │   • This is the "Big Picture" feature provided by React             │
    │   • Includes logic to create a "Storage Tank" → createContext()     │
    │   • Includes a "Delivery Man" → Provider                            │
    │                                                                     │
    ├─────────────────────────────────────────────────────────────────────┤
    │                                                                     │
    │   🪝 useContext                                                     │
    │   ─────────────                                                     │
    │   • This is a Hook (a specific tool)                                │
    │   • Used inside a component to GRAB data from the storage tank      │
    │   • Used to get data from provider or the context we created        │
    │                                                                     │
    └─────────────────────────────────────────────────────────────────────┘
    
    
    ⚠️  THE DISTINCTION:
        You can't use ⁡⁣⁣⁢useContext⁡ if you haven't set up the ⁡⁣⁣⁢Context API⁡ first!



┌──────────────────────────────────────────────────────────────────────────────┐
│  2️⃣   ⁡⁣⁢⁣THE SCENARIO: The "Family Secret Recipe" 👵⁡                           │
└──────────────────────────────────────────────────────────────────────────────┘

    Imagine a Great-Grandmother who has a secret recipe (Data) 📜


    ❌ WITHOUT CONTEXT (Prop Drilling):
    ────────────────────────────────────
    
        👵 Great-Grandmother
         │
         ▼ (passes recipe)
        👩 Daughter
         │
         ▼ (passes recipe)
        👨 Son
         │
         ▼ (passes recipe)
        👧 Granddaughter
    
        Even if the people in the middle don't cook, 
        they have to carry the paper!
        
        😫 This is "PROP DRILLING" and it's ANNOYING!


    ✅ WITH CONTEXT API:
    ─────────────────────
    
              ☁️ MAGIC CLOUD (Provider)
            ┌───────────────────────┐
            │   📜 Secret Recipe    │
            └───────────────────────┘
                      ▲
                      │
        Great-Grandmother puts the recipe 
        in the "Magic Cloud" above the house


    ✅ WITH useContext:
    ────────────────────
    
              ☁️ MAGIC CLOUD (Provider)
            ┌───────────────────────┐
            │   📜 Secret Recipe    │
            └─────────┬─────────────┘
                      │
                      ▼
            👧 "I'll take that recipe!" (The Hook)
            
        Any family member who wants to cook just looks up!
        People who don't care about cooking don't have to touch it.

    Since they work together, "When to use" isn't about choosing 
    one over the other, but rather knowing the STEPS:

    ╔═══════════╦═══════════════════════════╦═════════════════════════════════╗
    ║   STEP    ║       WHAT YOU USE        ║              WHY?               ║
    ╠═══════════╬═══════════════════════════╬═════════════════════════════════╣
    ║           ║                           ║                                 ║
    ║  1.CREATE ║  React.createContext()    ║  To define the "folder" where   ║
    ║           ║                           ║  your data will live            ║
    ║           ║                           ║                                 ║
    ╠═══════════╬═══════════════════════════╬═════════════════════════════════╣
    ║           ║                           ║                                 ║
    ║  2.PROVIDE║  <MyContext.Provider>     ║  To wrap your app (or section)  ║
    ║           ║                           ║  so data is available to all    ║
    ║           ║                           ║                                 ║
    ╠═══════════╬═══════════════════════════╬═════════════════════════════════╣
    ║           ║                           ║                                 ║
    ║  3.CONSUME║  useContext(MyContext)    ║  To actually GRAB that data     ║
    ║           ║                           ║  inside a specific component    ║
    ║           ║                           ║                                 ║
    ╚═══════════╩═══════════════════════════╩═════════════════════════════════╝

    │                                                                     │

    │                                                                     │
    │  🔐 USER AUTHENTICATION                                             │
    │     Knowing if user is "Logged In" and their "Username"             │
    │                                                                     │
    │     → Profile page needs it                                         │
    │     → Header needs it                                               │
    │     → Checkout page needs it                                        │
    │                                                                     │
    ├─────────────────────────────────────────────────────────────────────┤
    │                                                                     │
    │  🌍 LANGUAGE / LOCALIZATION                                         │
    │     If user chooses "Marathi" or "English"                          │
    │                                                                     │
    │     Every text component in the app needs to know that setting      │
    │                                                                     │
    └─────────────────────────────────────────────────────────────────────┘

🚨  THE PROBLEM: Re-Rendering
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    As a Senior Dev, I see juniors put EVERYTHING in Context to avoid 
    passing props. But there's a catch: Re-rendering!

    🎒 THE BACKPACK ANALOGY:
    ────────────────────────
    
    Imagine your Context is a giant backpack. Inside, you have:
    
        ┌─────────────────────────────────────────────────────────────────┐
        │                                                                 │
        │   👤 User's Name      →  Rarely changes                        │
        │                                                                 │
        │   ⏰ Timer/Clock       →  Changes EVERY SECOND!                 │
        │                                                                 │
        └─────────────────────────────────────────────────────────────────┘
    
    ❌ If you put BOTH in the same Context, every component "listening" 
       to the User's Name will ALSO refresh every single second because 
       the Timer is changing!


    ┌─────────────────────────────────────────────────────────────────────┐
    │                                                                     │
    │  🏆 THE GOLDEN RULE:                                                │
    │  ──────────────────                                                 │
    │                                                                     │
    │  Keep your Contexts SMALL and SPECIFIC!                             │
    │                                                                     │
    │  ✅ Have an AuthContext for login data                              │
    │  ✅ Have a ThemeContext for colors                                  │
    │  ❌ DON'T make one giant "EverythingContext"                        │
    │                                                                     │
    └─────────────────────────────────────────────────────────────────────┘

    💡 If you aren't careful, one tiny change can make your whole app 
       "flicker" (re-render) like a faulty lightbulb! 💡



┌──────────────────────────────────────────────────────────────────────────────┐
│  5️⃣   THE REALITY: Does Everyone Re-render?                                 │
└──────────────────────────────────────────────────────────────────────────────┘

    In your example, You have a Provider wrapping components A, B, C, and D:


            ┌─────────────────────────────────────────┐
            │         📦 PROVIDER                     │
            │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐        │
            │  │  A  │ │  B  │ │  C  │ │  D  │        │
            │  └─────┘ └─────┘ └─────┘ └─────┘        │
            └─────────────────────────────────────────┘


    📜 THE RULE:
    ─────────────
    If a component uses useContext hook to "listen" to that provider,
    and a value in that provider changes → that component WILL re-render.


    🤔 THE CONFUSION POINT:
    ────────────────────────
    What if Component B doesn't use the context? Does it still re-render?

    ┌─────────────────────────────────────────────────────────────────────┐
    │                                                                     │
    │  ⚠️  If the Provider's PARENT re-renders (meaning the file where   │
    │      you defined the state for the provider updates), then YES,     │
    │      by default, ALL children (A, B, C, D) might re-render!         │
    │                                                                     │
    │  React thinks: "The parent changed, so I should probably            │
    │                 check the kids."                                    │
    │                                                                     │
    └─────────────────────────────────────────────────────────────────────┘



┌──────────────────────────────────────────────────────────────────────────────┐
│  6️⃣   ⁡⁣⁢⁣𝗛𝗢𝗪 𝗧𝗢 𝗦𝗢𝗟𝗩𝗘 𝗧𝗛𝗘 "𝗠𝗔𝗦𝗦 𝗥𝗘-𝗥𝗘𝗡𝗗𝗘𝗥" 𝗣𝗥𝗢𝗕𝗟𝗘𝗠⁡                         │
└──────────────────────────────────────────────────────────────────────────────┘

    As a Senior Dev, I use THREE main "Shields" to protect performance:


    ╔═════════════════════════════════════════════════════════════════════╗
    ║                                                                     ║
    ║  🛡️  SHIELD 1: Split Your Contexts                                  ║
    ║      (The "Separate Folders" Approach)                              ║
    ║                                                                     ║
    ╠═════════════════════════════════════════════════════════════════════╣
    ║                                                                     ║
    ║  ❌ DON'T put "User Profile" and "App Theme" in same Provider       ║
    ║                                                                     ║
    ║  Why? If Theme changes (Light → Dark), you don't want your          ║
    ║       Profile component to re-render!                               ║
    ║                                                                     ║
    ║  ✅ SOLUTION:                                                       ║
    ║     Create a ThemeProvider and an AuthProvider                      ║
    ║     Wrap them like layers of an onion 🧅                            ║
    ║                                                                     ║
    ║         <AuthProvider>                                              ║
    ║             <ThemeProvider>                                         ║
    ║                 <App />                                             ║
    ║             </ThemeProvider>                                        ║
    ║         </AuthProvider>                                             ║
    ║                                                                     ║
    ║  Now, a change in Theme only talks to components listening to Theme!║
    ║                                                                     ║
    ╚═════════════════════════════════════════════════════════════════════╝


    ╔═════════════════════════════════════════════════════════════════════╗
    ║                                                                     ║
    ║  🛡️  SHIELD 2: React.memo                                           ║
    ║      (The "Did Anything Actually Change?" Shield)                   ║
    ║                                                                     ║
    ╠═════════════════════════════════════════════════════════════════════╣
    ║                                                                     ║
    ║  You can wrap a component (like Component B) in React.memo          ║
    ║                                                                     ║
    ║  📊 Scenario:                                                       ║
    ║     Component B is a heavy chart that doesn't use Context           ║
    ║                                                                     ║
    ║  💻 Code:                                                           ║
    ║     const ComponentB = React.memo(() => { ... });                   ║
    ║                                                                     ║
    ║  ✅ Result:                                                         ║
    ║     Even if Provider's parent re-renders, React will say:          ║
    ║     "Wait, your props haven't changed. You're good! Stay as you are"║
    ║                                                                     ║
    ║  It STOPS the re-render from trickling down! 🛑                     ║
    ║                                                                     ║
    ╚═════════════════════════════════════════════════════════════════════╝


    ╔═════════════════════════════════════════════════════════════════════╗
    ║                                                                     ║
    ║  🛡️  SHIELD 3: Move State Down                                      ║
    ║      (The "Cleanup" Approach)                                       ║
    ║                                                                     ║
    ╠═════════════════════════════════════════════════════════════════════╣
    ║                                                                     ║
    ║  ❌ Sometimes we wrap the ENTIRE app in a Provider when only        ║
    ║     the Navbar needs the data                                       ║
    ║                                                                     ║
    ║  ✅ SOLUTION:                                                       ║
    ║     Move the Provider as LOW as possible in the component tree      ║
    ║                                                                     ║
    ║     If only the "Settings" page needs specific data,                ║
    ║     only wrap the "Settings" page!                                  ║
    ║                                                                     ║
    ║     ❌ <AppProvider>           ✅ <App>                            ║
    ║           <App />                   <SettingsProvider>              ║
    ║        </AppProvider>                  <Settings />                 ║
    ║                                     </SettingsProvider>             ║
    ║                                  </App>                             ║
    ║                                                                     ║
    ╚═════════════════════════════════════════════════════════════════════╝

⁡⁢⁢⁢import React, { createContext, useContext, useState, memo } from 'react';⁡

  1. Create the Context
    ⁡⁢⁢⁢const CountContext = createContext();⁡

  2. The Provider Component
    ⁡⁢⁢⁢export const CountProvider = ({ children }) => {
        const [count, setCount] = useState(0);

        return (
            <CountContext.Provider value={{ count, setCount }}>
            {children}
            </CountContext.Provider>
        );
    };⁡

   3. Component A: This one LISTENS to Context
    ⁡⁢⁢⁢const Header = () => {
        const { count } = useContext(CountContext);
        console.log("Header Rendered! (I need the count)");
        return <h1>Current Count: {count}</h1>;
    };⁡

    4. Component B: The "Optimized" Footer
      - We wrap it in memo() so it only re-renders if its OWN props change.
      - Since it has no props and doesn't use useContext, it stays frozen!
    ⁡⁢⁢⁢const Footer = memo(() => {
        console.log("Footer Rendered! (Wait... I shouldn't be rendering)");
        return <footer>I am just a simple footer.</footer>;
    });⁡
    
     5. The App
        ⁡⁢⁢⁢export default function App() {
            return (
                <CountProvider>
                <Header />
                <hr />
                <CounterButton />
                <Footer />
                </CountProvider>
            );
        }

        const CounterButton = () => {
            const { setCount } = useContext(CountContext);
            return <button onClick={() => setCount(prev => prev + 1)}>Add +1</button>;
        };⁡

    # What's happening here?

        - Header: Every time you click the button, the count changes. Because Header uses useContext(CountContext), it says, "Hey, my data changed! I need to re-draw myself."

        - Footer: Even though it is inside the CountProvider, it is wrapped in memo. Since it doesn't use the count data, React looks at it and says, "Nothing changed for you, buddy. Stay as you are."

        > Without memo, the Footer would print "Footer Rendered!" in the console every single time you clicked the button. With memo, it only prints it once (when the app first starts).
