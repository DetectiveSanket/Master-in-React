## ⁡⁢⁣⁣𝘂𝘀𝗲𝗘𝗳𝗳𝗲𝗰𝘁 𝙃͟𝙤͟𝙤͟𝙠͟𝙨 𝗮𝗻𝗮𝗹𝗼𝗴𝘆.⁡

    * Imagine you're a chef. Your job is to cook a dish and plate it. That's the render — React figures out what the UI should look like and puts it on the plate.

    - Now, after the plate goes out to the customer — after the customer can already see it — your assistant walks in and says: "The order is done. Now I'll go update the kitchen inventory, log the order, and call the supplier if we're running low."

    ^ That assistant is useEffect.

    * The key thing: the assistant doesn't run while you're cooking. The assistant doesn't run while the plate is being carried out. The assistant runs only after the customer already has the plate in front of them — after the browser has painted the screen.

    ^ That's useEffect. React renders, the browser paints, then the effect runs.

------------------------------------------------------------------------------------------------------------------------------

• ⁡⁣⁢⁣𝗧𝗵𝗲 𝗼𝗻𝗲 𝗰𝗼𝗿𝗲 𝘁𝗿𝘂𝘁𝗵:⁡

   - useEffect runs after ⁡⁣⁣⁢React has updated the DOM and after the browser has painted⁡. Your component has already shown its output to the user before the effect touches anything.

------------------------------------------------------------------------------------------------------------------------------

• ⁡⁣⁢⁣𝗘𝘅𝗮𝗺𝗽𝗹𝗲 𝗔 — 𝗪𝗮𝘁𝗰𝗵 𝘁𝗵𝗲 𝘀𝗲𝗾𝘂𝗲𝗻𝗰𝗲⁡

⁡⁢⁢⁢    function Timer() {
        const [count, setCount] = useState(0);

        useEffect(() => {
            // This line runs AFTER the browser has already painted
            // The user already sees the updated count on screen before this fires
            console.log("Effect ran. Current count:", count);
        }, [count]); // Re-runs only when count changes

        return (
            <button onClick={() => setCount(count + 1)}>
            Count: {count}  {/* This updates on screen first */}
            </button>
        );
    }⁡

    > 𝗧𝗵𝗲 𝘀𝗲𝗾𝘂𝗲𝗻𝗰𝗲 𝗲𝘃𝗲𝗿𝘆 𝘀𝗶𝗻𝗴𝗹𝗲 𝘁𝗶𝗺𝗲 𝘆𝗼𝘂 𝗰𝗹𝗶𝗰𝗸:

        1. setCount triggers a re-render
        2. React re-runs the component function — calculates new output
        3. React updates the DOM
        4. Browser paints — user sees Count: 1 on screen
        5. Only now — useEffect fires and logs "Effect ran. Current count: 1"

    - The effect always sees the world after the user already has.

------------------------------------------------------------------------------------------------------------------------------

• ⁡⁣⁢⁣𝗘𝘅𝗮𝗺𝗽𝗹𝗲 𝗕 — 𝗪𝗵𝗮𝘁 𝗯𝗿𝗲𝗮𝗸𝘀 𝘄𝗶𝘁𝗵𝗼𝘂𝘁 𝘁𝗵𝗶𝘀 𝘀𝗲𝗽𝗮𝗿𝗮𝘁𝗶𝗼𝗻⁡

    // Imagine if useEffect ran DURING render — this is what would happen:

⁡⁢⁢⁢    function BadComponent() {
        const [data, setData] = useState(null);

        // If this ran during render, React would be frozen here
        // waiting for the API before showing ANYTHING to the user
        fetch('/api/data')
            .then(res => res.json())
            .then(json => setData(json));

        return <div>{data ? data.title : "Loading..."}</div>;
    }
    // This also causes an infinite loop —
    // fetch → setData → re-render → fetch → setData → ...⁡

    * useEffect solves both problems — it runs after paint so the UI isn't blocked, and React controls when it runs so you don't get infinite loops.

------------------------------------------------------------------------------------------------------------------------------

• Purpose of useEffect:

    - To run side effects after the component has rendered and the browser has painted.
    - The actual goal is: synchronize your component with something outside React — an API, a timer, a WebSocket, a DOM element, an event listener. Anything external.
    - The dependency array controls when that synchronization happens. That's it.
